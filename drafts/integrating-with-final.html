Final · integration guide · client-only apps

Integrating with Final

A user approves your app once per install. From then on your app holds a connection to that user's Final Balances reserved to you: create sub-balances, ask for deposit instructions, issue a card, and watch money move, all through the same REST routes with one extra header. Everything here runs on the device; no backend is needed.

Status: pre-release. Shapes below are the target contract and may still shift before going live. Field names, error codes and event names are stable enough to build against; the base URL is not final.

Conventions

Base URL
https://api.final.net/v1 is a placeholder; the production host will be confirmed before you go live. Keep it in one config value, as the helpers below do. JSON in and out.
Amounts
Smallest-unit integer strings: "100000000" is 1 ZEC (8 decimals) and "1000000000" is 1 USDe (9 decimals), so scale by the Balance's own asset, never by a constant. Balance, Transaction and deposit amounts carry a display_* sibling for humans: the decimal figure alone, "2.50000000", with no ticker or currency sign. Compute against the integer.
Assets
CAIP-19 ids: solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp/token:<mint>.
Lists
{ data: [...], has_more, after_cursor }; page with ?limit=&after_cursor=.
Retries
Send Idempotency-Key: <uuid> on any POST you might retry; a replay returns the first response. Retry with the same key whenever you do not know whether the request completed — a timeout, a dropped connection, the app suspended mid-flight — which is the case the key exists for. Mint a new key only when the server actually answered and you want a fresh attempt: an answered 5xx is recorded like any other response, so the same key replays that error instead of re-running the request.
Times
RFC 3339 UTC strings (created_at, expires_at, …).

Keys and headers

Your app ships a publishable key: final_publishable_live_… or final_publishable_test_…. It identifies your app and nothing more; a _test_ key sees test-mode data only and unlocks the simulations under Test mode. Every request carries it:

Authorization: Bearer final_publishable_live_…

Connecting a user yields a client_secret, one per install, stored in the Keychain / Keystore. It is the connection id with a secret half appended, so you store one string:

connection_01j6b3v8x2q7k9m4n5p6r7s8t9_secret_a91c7e4d2f0b9c6e3a1f7d5b8c2e4f6a…
└─────────────── id ────────────────┘└──────┘└─────────── secret ───────────┘

The id is everything before the literal _secret_; neither half can contain that token (the id is a 26-character base32 ULID, the secret is hex), so split("_secret_") is safe. activate also returns id as its own field if you would rather store both and never split.

Every request on behalf of that user carries it in one more header:

Final-Connection: connection_01j6b3v8x2q7k9m4n5p6r7s8t9_secret_a91c7e4d2f0b9c6e3a1f7d5b8c2e4f6a…

The one request helper every example uses

// OkHttp + kotlinx.serialization; a suspend function, so it never runs on the main thread
const val FINAL_API = "https://api.final.net/v1"          // placeholder host; confirmed before go-live
val http = OkHttpClient(); val json = Json { ignoreUnknownKeys = true }
suspend fun finalRequest(method: String, path: String, body: JsonObject? = null, connection: String? = null,
                         headers: Map<String, String> = emptyMap()): JsonObject =
    withContext(Dispatchers.IO) {
        val req = Request.Builder().url("$FINAL_API/$path")
            .header("Authorization", "Bearer $PUBLISHABLE_KEY")
            .apply { connection?.let { header("Final-Connection", it) }; headers.forEach { (k, v) -> header(k, v) } }
            .method(method, body?.let { json.encodeToString(it).toRequestBody("application/json".toMediaType()) }
                ?: if (method == "POST") ByteArray(0).toRequestBody() else null)   // OkHttp refuses a POST with no body; the bodiless routes take an empty one
            .build()
        http.newCall(req).execute().use { json.parseToJsonElement(it.body!!.string()).jsonObject }
    }
// URLSession
let api = URL(string: "https://api.final.net/v1")!         // placeholder host; confirmed before go-live
func finalRequest(_ method: String, _ path: String, body: [String: Any]? = nil, connection: String? = nil,
                  headers: [String: String] = [:]) async throws -> (status: Int, body: [String: Any]) {
    var r = URLRequest(url: api.appending(path: path)); r.httpMethod = method
    r.setValue("Bearer \(publishableKey)", forHTTPHeaderField: "Authorization")
    r.setValue("application/json", forHTTPHeaderField: "Content-Type")
    if let connection { r.setValue(connection, forHTTPHeaderField: "Final-Connection") }
    headers.forEach { r.setValue($1, forHTTPHeaderField: $0) }
    if let body { r.httpBody = try JSONSerialization.data(withJSONObject: body) }
    let (data, resp) = try await URLSession.shared.data(for: r)
    return ((resp as! HTTPURLResponse).statusCode, try JSONSerialization.jsonObject(with: data) as! [String: Any])
}

Connect

  1. Generate a PKCE pair and propose with the challenge (POST /intents). The response names the connection id; no secret exists yet.
  2. Open approval_url in the system browser. The user signs in to Final and approves with a passkey.
  3. Final returns to your URL scheme with a one-time code.
  4. Activate: exchange code + code_verifier for the client_secret (POST /connections/{id}/activate). It is issued once, only to the caller holding both halves.

A publishable key is public, so this is what makes the credential yours: whoever proposed keeps the verifier, and only your registered scheme receives the code.

PKCE is six lines; no library needed

val verifier  = ByteArray(32).also { SecureRandom().nextBytes(it) }.let { Base64.getUrlEncoder().withoutPadding().encodeToString(it) }
val challenge = Base64.getUrlEncoder().withoutPadding()
    .encodeToString(MessageDigest.getInstance("SHA-256").digest(verifier.toByteArray(Charsets.US_ASCII)))   // S256
import CryptoKit
let verifier  = Data((0..<32).map { _ in UInt8.random(in: 0...255) }).base64URLEncoded()
let challenge = Data(SHA256.hash(data: Data(verifier.utf8))).base64URLEncoded()   // S256
extension Data { func base64URLEncoded() -> String { base64EncodedString().replacingOccurrences(of: "+", with: "-").replacingOccurrences(of: "/", with: "_").replacingOccurrences(of: "=", with: "") } }

Kotlin (Android)

Custom Tabs for the browser, an intent-filter for zodl://final/return on an activity declared android:launchMode="singleTask" so the redirect reaches onNewIntent of the activity that stashed the verifier, not a fresh one.

Prefer a verified App Link on Android. Register https://zodl.example/final/return with an assetlinks.json instead of a custom scheme and use that as redirect_uri. Android verifies the domain, so no other app can claim the callback; a custom scheme is first come, first served. iOS gets the same guarantee only from 17.4 (ASWebAuthenticationSession.Callback.https), which is why the examples use a scheme on both platforms.

val created = finalRequest("POST", "intents", body = buildJsonObject {
    put("kind", "account.connect")
    putJsonObject("payload") {
        putJsonArray("assets") { add(ZEC) }
        put("code_challenge", challenge)
        put("redirect_uri", "zodl://final/return")
    }
})
val connectionId = created["connection"]!!.jsonObject["id"]!!.jsonPrimitive.content
securePrefs.edit { putString("final_pending", "$connectionId|$verifier") }   // EncryptedSharedPreferences; no secret exists yet

CustomTabsIntent.Builder().build()
    .launchUrl(this, Uri.parse(created["intent"]!!.jsonObject["approval_url"]!!.jsonPrimitive.content))

// Back in onNewIntent for zodl://final/return?intent_id=…&code=…
val code = intent.data!!.getQueryParameter("code")!!
val (id, verifier) = securePrefs.getString("final_pending", null)!!.split("|")
val activated = finalRequest("POST", "connections/$id/activate", body = buildJsonObject {
    put("code", code); put("code_verifier", verifier)
})                                                                          // 409 activation_code_expired → start over
keystore.put("final_connection", activated["client_secret"]!!.jsonPrimitive.content)   // the only thing to keep

Swift (iOS)

ASWebAuthenticationSession for the browser; the session closes itself when Final navigates to your scheme.

SFSafariViewController works too. If you already present links that way and receive universal links in onOpenURL, register an https return URL with Final instead of a scheme and keep that pattern; it is domain-verified, and it works on iOS 16. The caveat is cookies: since iOS 11 SFSafariViewController has its own store per app, so the user signs in to Final once inside your app rather than reusing a Safari session. ASWebAuthenticationSession with prefersEphemeralWebBrowserSession = false shares Safari's, and hands you the callback URL directly with no deep-link plumbing. Passkeys work in both.

                                             callbackURLScheme: "zodl") { url, error in

    session.prefersEphemeralWebBrowserSession = false                        // reuse the user's Final session

let code = URLComponents(url: callback, resolvingAgainstBaseURL: false)!.queryItems!.first { $0.name == "code" }!.value!

guard activated.status == 200 else { /* 409 activation_code_expired → start over */ return }

Tor. Every request in this doc works over Tor. The stream is the exception: it is one long-lived HTTP response, which a request/response Tor client cannot carry. When the user has Tor on, either open the stream over clearnet or skip it and poll GET /connections/{id}, GET /balances and GET /cards instead.

Kotlin: OkHttp's EventSource

val req = Request.Builder().url("$FINAL_API/connections/$connectionId/events")
    .header("Authorization", "Bearer $PUBLISHABLE_KEY")
    .header("Final-Connection", secret)
    .apply { lastEventId?.let { header("Last-Event-ID", it) } }
    .build()
EventSources.createFactory(http).newEventSource(req, object : EventSourceListener() {
    override fun onEvent(es: EventSource, id: String?, type: String?, data: String) {
        id?.let { lastEventId = it }
        val obj = json.parseToJsonElement(data).jsonObject["object"]!!.jsonObject
        when (type) {
            "connection.active"  -> refreshBalances()                     // GET /balances; the frame only confirms you are connected
            "deposit.credited"   -> refreshBalances()                     // credited, not confirmed: the ledger entry exists only here
            "card.activated"     -> showCard(obj)
            "card_auth.approved" -> toast("Card used at ${obj["merchant_name"]}")
        }
    }
    override fun onFailure(es: EventSource, t: Throwable?, r: Response?) { /* 403 → Connect again; else reconnect with Last-Event-ID */ }
})

Swift: URLSession.bytes

SSE is three line prefixes and a blank line.

var stream = URLRequest(url: api.appending(path: "connections/\(connectionId)/events"))
stream.setValue("Bearer \(publishableKey)", forHTTPHeaderField: "Authorization")
stream.setValue("text/event-stream", forHTTPHeaderField: "Accept")
stream.setValue(secret, forHTTPHeaderField: "Final-Connection")
if let last = lastEventId { stream.setValue(last, forHTTPHeaderField: "Last-Event-ID") }

do {
    let (bytes, _) = try await URLSession.shared.bytes(for: stream)
    var event = "", data = ""
    for try await line in bytes.lines {
        if line.hasPrefix("id:")         { lastEventId = String(line.dropFirst(3)).trimmingCharacters(in: .whitespaces) }
        else if line.hasPrefix("event:") { event = String(line.dropFirst(6)).trimmingCharacters(in: .whitespaces) }
        else if line.hasPrefix("data:")  { data += line.dropFirst(5) }
        else if line.isEmpty, !data.isEmpty {
            let object = (try JSONSerialization.jsonObject(with: Data(data.utf8)) as! [String: Any])["object"] as! [String: Any]
            switch event {
            case "connection.active":  await refreshBalances()               // GET /balances; the frame only confirms you are connected
            case "deposit.credited":   await refreshBalances()               // credited, not confirmed: the ledger entry exists only here
            case "card.activated":     showCard(object)
            case "card_auth.approved": toast("Card used at \(object["merchant_name"]!)")
            default: break
            }
            (event, data) = ("", "")
        }
    }
} catch { /* HTTP 403 → Connect again; otherwise reopen with Last-Event-ID */ }

Routes

Every route takes Authorization. Routes marked + connection also take Final-Connection, and every one of them can answer 404 connection_not_found (bad or missing secret), 403 connection_revoked, or 403 verification_pending (the account is under review, see Gates) before the route itself runs; those three are not repeated below. Sending Final-Connection to a route not marked this way, POST /intents or activation, is 400 connection_header_unexpected. A Balance or card outside your grant is a plain 404 not_found, the same as one that does not exist.

Exchange the code from the redirect and your verifier for the client_secret. Issued once.

Request
{
  "code": "…",             // from ?code= on the redirect; valid 10 minutes
  "code_verifier": "…"     // the one whose hash you proposed with

Response 200
{
  "id": "connection_…",
  "client_secret": "connection_…_secret_…"   // store it; never shown again

The only response that can never be reissued: the code is spent and Final keeps just the hash. An Idempotency-Key is how you make a lost one recoverable — retrying with the same key hands the secret back. Without a key there is nothing to replay, and a lost response means the user approves again. Both are fine; pick knowingly.

Direct deposit

For USDe this is the only way in: nothing swaps into it, so the pinned swap (swap_via, POST deposit_instructions) does not apply to a USDe Balance.

Besides a pinned swap, a user can send the asset itself to their own Final address from any wallet or exchange. Nobody accepts a deposit that arrives this way: Final credits it to whichever Balance it routes to, takes its fee, and announces the credit. Your app gets a say over routing when the user grants it, by proposing with "direct_deposit": true. The approval page asks for it and states the fee; without it every route below is a plain 404 balance_not_found.

  1. The address. GET /balances/{id}/deposit_instructions carries an onchain_address instruction (Deposit instructions) once your grant has the permission; without it you get the swap rails only. It is the user's account, not your Balance's: every Balance of that asset on the account, the user's own and each app's, shares one token account.
  2. Where it goes. A landing routes by the moment it landed: to the window covering that moment, else the account's default Balance for the asset, else its only Balance, else its oldest. Read which rule is in force with GET deposit_routing.
  3. Point it at your Balance. Reading the address does this: it opens a window routing the account's landings to your Balance for the next hour, and reading it again inside that hour extends the window. An account has one window at a time, shared with the user and every other app, so while another is open the read carries no address and deposit_in_progress.ends_at says when to try again: wait it out, or ask the user. Reading the address never makes your Balance the default; that is POST deposit_routing/default, and the user, or another app, can move it.
  4. The credit. deposit.credited arrives on the stream once the fee is taken. A landing worth less than the floor (minimum_fiat, in cents) waits, never expires, and credits together with whatever lands beside it on the same route. GET deposit_receipts shows every landing routed to your Balance, including the ones still waiting and why.

Final's fee is fee_basis_points of each deposit, taken from what landed, whichever Balance it routes to. Revoking the grant or the connection closes your windows at that moment, and a grant revocation also clears a default naming your Balance; what landed inside a window before that still credits you.

Gates: when the user has to do something

The approval is normally the only time the user leaves your app. Consent is sign in and a passkey, and that same passkey activates the user's wallet for every asset you asked for, so money moves without a second trip. Identity and card terms are collected when the user signs up for Final and verified asynchronously; you never collect either. When Final does still need something from the user, the money route answers 403 user_action_required with a URL in detail:

{
  "error": {
    "type": "permission",
    "code": "user_action_required",
    "message": "…",
    "detail": {
      "url": "https://final.net/balance/balance_…/activate?connection_id=…"
    }
  }
}

Open detail.url the same way you opened the approval (Custom Tab / ASWebAuthenticationSession). The user finishes on Final, is returned to your scheme with ?balance_id=…, and you call again. Two codes cover everything a money route can ask for:

CodeMeaningWhat to do
403 user_action_requiredthe user has to finish something on Final before this can proceedopen detail.url; call again when they return
403 verification_pendingFinal is verifying this account; every call on this connection waits, reads includedshow "verification in progress"; retry later. No URL
Both carry "type": "permission".

There is no readiness probe; the error is the signal.

iOS 18 to move money. The approval unlocks the user's wallet key with a passkey (WebAuthn PRF), which Safari supports from iOS 18. On iOS 16 and 17 the connection and Balance reads work; deposits and cards need the wallet, so they need iOS 18. Android has no such floor.

Trying it from a terminal

To poke at the API with curl before there is an app to receive a redirect: in test mode, from a profile with no registered redirect, propose without a redirect_uri; with one registered, omitting it on the proposal just falls back to it. Final then shows the user an "approved" screen instead of redirecting, and for the next 10 minutes POST /connections/{id}/activate accepts { "code_verifier" } alone, with no code, and returns the client_secret. This exists only for that; livemode always requires the redirect.

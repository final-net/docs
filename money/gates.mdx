The approval is normally the only time the user leaves your app. Consent is sign in and a passkey, and that same passkey readies the user's wallet for every asset you asked for when it can, so money moves without a second trip. Identity and card terms are collected when the user signs up for Final and verified asynchronously; you never collect either.

When Final still needs something from the user, a money route answers `403` with one of two codes. Both carry `"type": "permission"`.

| Code | Meaning | What to do |
| --- | --- | --- |
| `user_action_required` | The user has to finish something on Final before this can proceed. | Open `detail.url`; call again when they return. |
| `verification_pending` | Final is verifying this account. Only Final can move it. | Show "verification in progress"; retry later. No URL. |

```json
{
  "error": {
    "type": "permission",
    "code": "user_action_required",
    "message": "…",
    "detail": { "url": "https://final.com/balance/balance_…/activate?connection_id=…" },
    "request_id": "req_…"
  }
}
```

There is no readiness probe. The error is the signal, and a first money call after consent can still answer `user_action_required`.

## The return trip

Open `detail.url` the way you opened the approval: a Custom Tab, or `ASWebAuthenticationSession`. The user finishes on Final and is returned to the same redirect your connection was proposed with, carrying `?balance_id=…`. Then call again.

<CodeGroup>

```kotlin Kotlin
val res = finalRequest("POST", "cards", connection = secret, body = body,
    headers = mapOf("Idempotency-Key" to UUID.randomUUID().toString()))
val err = res.body?.get("error")?.jsonObject
when {
    res.status == 201 || res.status == 200 -> showCard(res.body!!["card"]!!.jsonObject)
    err?.get("code")?.jsonPrimitive?.content == "user_action_required" ->
        openOnFinal(err["detail"]!!.jsonObject["url"]!!.jsonPrimitive.content) // returns on yourapp://final/return?balance_id=…; call again
    err?.get("code")?.jsonPrimitive?.content == "verification_pending" -> banner("Verification in progress")
}
```

```swift Swift
let res = try await finalRequest("POST", "cards", body: body, connection: secret,
                                 headers: ["Idempotency-Key": UUID().uuidString])
if res.status == 201 || res.status == 200 {
    showCard(res.body!["card"] as! [String: Any])
} else if let err = res.body?["error"] as? [String: Any], err["code"] as? String == "user_action_required",
          let url = (err["detail"] as? [String: Any])?["url"] as? String {
    try await openOnFinal(URL(string: url)!) // returns on yourapp://final/return?balance_id=…; call again
} else if (res.body?["error"] as? [String: Any])?["code"] as? String == "verification_pending" {
    banner("Verification in progress")
}
```


## Which routes gate

- `POST /balances/{id}/deposit_instructions`, and `GET` once your grant has `direct_deposit`: the identity gate. Reads of the Balance itself never gate.
- `POST /cards`: identity, the issuing terms, and an address on file when you send no `cardholder_info`.
- A card swipe passes through no call of yours, so a gate there arrives as a `card_auth.declined` event with `reason: "user_action_required"` and the same `detail.url`.

`verification_pending` blocks reads too, but only during an account review hold: while that holds, every call on the connection answers it before the route runs. During an identity check reads work and a card write answers `user_action_required`.

## Region

Two more `403` codes can arrive before any route runs, with `"type": "compliance"`: `region_not_supported`, when the request comes from a region Final does not serve, and `region_unverified`, when the region could not be established. Neither is something the user can clear from your app.

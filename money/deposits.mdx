A user funds a Balance by sending the asset to their own Final address from any wallet or exchange. Your app gets a say over where it lands when the user grants it, by proposing with `"direct_deposit": true`. The approval page asks for it and states the fee; without it the deposit instructions carry no address and every routing and receipt route is `404 balance_not_found`.

## Deposit instructions

`GET /balances/{id}/deposit_instructions` is a pure read. Money lives on the root, so asking any Balance in a tree answers for its root, and `balance_id` in the response is the root's.

- `address` is the user's own wallet, which is what a sender enters. `token_account` is where the asset lands; every Balance of that asset on the account shares it. Pasting `token_account` where `address` belongs sends funds somewhere unreachable.
- `minimum_fiat` is the floor in the smallest unit of `fiat_currency`. A landing worth less waits and credits together with whatever lands beside it.
- `fee_basis_points` is Final's fee, taken from what landed.
- Optional fields are absent, never `null`. Two can appear beside the list: `delegation_required: true`, when the user has a step to finish on Final before the address can be used, and `deposit_in_progress: { "ends_at", "balance_id"? }`, when another Balance's routing window holds the account and the address is withheld until it ends. `balance_id` is present only when your own connection opened that window.
- Reading the address claims the next hour's landings for your Balance; see routing below.

| Status | Code | Meaning |
| --- | --- | --- |
| 403 | `user_action_required`, `verification_pending` | The identity gate. See [Gates](/money/gates). |
| 404 | `not_found` | The Balance is outside your grant. |

## Where a landing goes

A landing routes by the moment it landed: to the window covering that moment, else the account's default Balance for the asset, else its only Balance, else its oldest. `GET /balances/{id}/deposit_routing` reads which rule is in force:

import { DepositRouting } from '/snippets/objects/deposit-routing.mdx';

<DepositRouting />

- `POST /balances/{id}/deposit_routing/default` makes this root the default for its asset. Replaces whatever the default was. Answers the routing, as the read does.
- `POST /balances/{id}/deposit_routing/overrides` opens a window: `{ "ends_at": "…" }`, an hour from now by default and at most 24 hours. An account has one window at a time, shared with the user and every other app, so a second is `409 override_in_flight`. `{ "replace_active": true }` closes a window your own connection opened and opens the new one in its place. Send an `Idempotency-Key`.
- `DELETE /balances/{id}/deposit_routing/overrides/{override_id}` closes your window now. What landed inside it still routes to you. A window you did not open is `404 override_not_found`.

Reading the address opens a window too, and reading it again inside that hour extends it. Reading the address never makes your Balance the default.

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | `ends_at_out_of_range` | In the past, or more than 24 hours out. |
| 404 | `balance_not_found` | Not a root in your grant, or no `direct_deposit` on the grant. |
| 409 | `override_in_flight` | A window is already open. Wait for its `ends_at`, or `replace_active` if it is yours. |
| 503 | `direct_deposit_unavailable` | Direct deposit is paused. Retry shortly. |

## The credit

`deposit.credited` arrives on the stream or by webhook once the fee is taken, carrying `batch_id`. Then `GET /balances/{id}` shows the new `available`, though it can lag the event briefly.

## The swap rail

Some assets can also be funded by sending a different asset, which a partner swaps in. `GET /assets` lists a `swap_via` shape for those. `POST /balances/{id}/deposit_instructions` pins an exact-amount swap:

```json
{ "inbound_amount": "100000000" }
```

Exactly one of `inbound_amount`, what the user will send, or `outbound_amount`, what they want credited, in smallest units. The response carries a [swap instruction](/reference/objects/swap-instruction) with the pinned amounts and `expires_at`. The user must send exactly the pinned inbound amount before it expires. Send an `Idempotency-Key`, since a retry must not allocate twice. The `display_*` figures on this response are the partner's; on the read they carry the asset's full decimals.

USDe has no swap rail: `POST` on a USDe Balance answers `400 no_inflow_route`.

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | `invalid_amount` | Missing, both, or not a positive integer string. |
| 400 | `no_inflow_route` | Nothing swaps into this asset in this mode. |
| 400 | `test_behavior_not_allowed` | `Final-Test-Behavior` on a live credential. |
| 403 | `user_action_required`, `verification_pending` | See [Gates](/money/gates). |

## Exchange rate

`GET /exchange_rate?base=<asset>&quote=iso4217:USD` answers an [exchange rate](/reference/objects/exchange-rate): the quote currency per one unit of the base, as a decimal string. It is a quote for display, not a promise: deposits pin their own amounts and card spend converts at authorization.

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | `base_required`, `quote_required` | A side is missing. |
| 400 | `asset_unknown` | Not a fiat unit or an asset Final knows. |
| 400 | `pair_unpriceable` | No rate for this pair, or the upstream read failed. |
| 503 | `rates_unavailable` | No rate source is configured. |

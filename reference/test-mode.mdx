---
title: "Test mode"
description: "Simulated Balances, test deposits and test authorizations"
---

Use your `final_publishable_test_…` or `final_test_…` key. Every route and event behaves as in live mode, against test-mode data, with no real money and no card network. Two things that happen in the outside world, a deposit landing and a card being swiped, do not happen on their own. You trigger them.

## Simulated Balances

A test credential opens a Balance in the same asset ids a live one does. Such a Balance is simulated: it has no address on any chain, and its money is ledger entries alone. `GET /assets` on a test key lists the live assets alongside the test ones.

Its deposit instructions carry the live shape, with the asset's real `mint`, `minimum_fiat`, `fiat_currency` and `fee_basis_points`, so your deposit screen renders unchanged. The `address` and `token_account` are one fixed placeholder that no wallet accepts, since it is not a valid address. Nothing can be sent to it; the test deposit below stands in for the sender. `delegation_required` and `deposit_in_progress` never appear on a simulated Balance, and routing windows and receipts are not simulated: those routes answer `404 balance_not_found`.

A simulated Balance has no swap rail, so `POST /balances/{id}/deposit_instructions` answers `400 no_inflow_route`.

## A deposit landing

`POST /balances/{id}/test_deposits` credits a simulated Balance as if the asset had landed:

```json
{ "amount": "1000000000" }
```

The amount is in the asset's smallest unit. The response is `{ "deposit": { "id", "balance_id", "asset", "amount", "status": "credited", … } }` with `201`. Any Balance in the tree may be named; money lands on the root, and `deposit.credited` names the one you asked for as `requested_balance_id`. A provisioning card on the tree activates, `card.activated` follows, and `GET /balances/{id}` shows the new `available`. Send an `Idempotency-Key`.

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | `test_behavior_not_allowed` | A live credential. |
| 400 | `balance_not_simulated` | A test-mode Balance on a test asset, which has a real chain. |
| 400 | `invalid_amount` | Not a positive integer string. |
| 409 | `balance_closed` | The Balance is closed. |

## A card being used

`POST /cards/{id}/test_authorizations` runs the real authorization decision and settlement on a test-mode card:

```json
{
  "amount": "1899",
  "currency": "iso4217:USD",
  "asset_amount": "18990000000",
  "merchant_name": "Blue Bottle",
  "merchant_category": "5812",
  "merchant_country": "US"
}
```

`amount` is what the merchant charges, in the currency's smallest unit; `currency` defaults to `iso4217:USD`. `asset_amount` is what the swipe pulls from the Balance, in the asset's smallest unit. Final records no rate, so you send both. `merchant_name` is required, since limits match on it.

The response is a [test authorization](/reference/objects/test-authorization), with `decline_reason` on declines only. Then `card_auth.approved` and `card_auth.settled` arrive, or `card_auth.declined` with nothing to settle. There is no way to force the answer: a decline comes from the card or the Balance declining, so freeze the card for `card_frozen` or ask for more than `available` for `insufficient_funds`.

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | `invalid_amount`, `merchant_name_required` | The body. |
| 404 | `not_found` | A live-mode or closed card. |
| 409 | `card_provisioning` | The card has not activated. Fund the Balance first. |

## Everything else

The passkey approval, the activation, the stream, the gates and the errors are the real code path. A test-mode key never sees live data and vice versa.

From a terminal, test mode also lets you activate without a redirect; see [From an app](/connect/from-an-app#trying-it-from-a-terminal).
